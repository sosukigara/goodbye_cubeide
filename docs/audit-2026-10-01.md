### S1-2 · Live CSV エクスポートがローテート済みセッション CSV 全体をホストスレッドで読み込む · **確度: 証明済み（PROVABLE）**

`src/extension.ts:1530-1534`:

```ts
const fromFile = this.readSessionCsv();
const body = fromFile ?? formatCsv(this.samples);
const rows = body.split("\n").filter((l) => l.trim() !== "").length - 1;
const uri = vscode.Uri.joinPath(folder.uri, "live.csv");
await vscode.workspace.fs.writeFile(uri, Buffer.from(body, "utf8"));
```

および `src/extension.ts:1548`: `text = readFileSync(this.csvPath, "utf8");`

**規模（リポジトリ自身のローテーション式から算出）**. `scripts/live_poll.py:585-591` は
`CSV_MAX_ROWS = 100000`、`CSV_MAX_ROWS_CAP = 5_000_000`、`CSV_WINDOW_S = 120` を設定し、
`csv_rotation_limit`（`:594-605`）は `min(max(100000, hz * leaves * 120), 5e6)`。
ユーザの 220 leaves × 100 Hz では `2_640_000` 行 — ローテーション間の**ファイル全体**、
約 193 MB。1 回の押下が行うのは: 193 MB の `readFileSync`、
行を**数えるためだけ**に走る 264 万要素の `.split("\n")`、そして再度 193 MB の `Buffer.from`。
すべて拡張機能のホスト**メインスレッド**上 — 10ms の `tailTimer`（`:1174-1177`）を
回しているのと同じスレッド。500 MB 超のピーク RSS で数秒単位のウィンドウフリーズになり、
進行中の既定値変更（50→100 Hz）で 96 MB から倍増する。

**最小修正**: `exportCsv` / `readSessionCsv` 内の 2 点のみ。

1. `body.split("\n")` による行数カウントを削除する。コピーするチャンクごとに
   改行出現数を合計して数える。
2. `readFileSync` + `Buffer.from` ではなく、`tailOnce` が既に使っている形
   （`src/extension.ts:1213-1226`）で 8 MB チャンクの fd を読み、`write` ストリームへ流す。

ストリーミング実装を dispatch する気がないなら、安価で正しいゲートはしきい値での拒否:
`statSync(this.csvPath).size > 64 * 1024 * 1024` →
`showWarningMessage` で `build-ext/live.csv` が完全忠実な原本であると明示した上で拒否。
これは正直でテスト可能。

**回帰テスト**: サイズゲート用の `tests/export-csv.test.ts`（しきい値超の一時 CSV を書き、
拒否と `writeFile` 未呼び出しを assert）、およびストリーミングコピーについては
複数チャンクのファイルで書き込みバイト列が元と一致することを assert。

## レート / CSV / ディスク Implications（100 Hz 変更を、リポジトリ自身の定数に対して実測）

`ARCHIVE_MAX = 20000`（`src/extension.ts:1717`）は系列ごとの cap ではなく
**全系列**|flats である点が重要: Rows/s = `hz × nSeries` なので CSV 窓は
`200 / nSeries` 秒になる — 1 系列で 200 秒、5 で 40 秒、10 で 20 秒、**20 で 10 秒**。
`stm32-ext/README.md:157`（「系列の履歴はホスト側に最大 20000 行まで保持され」）は字義は正しいが、
「履歴は十分」と読めてしまう。100 Hz で 20 系列のとき CSV 保存ボタンが得られるのは 10 秒しかないのに
グラフ自身の 60 秒セレクタは 60 秒を主張する — 2 つのサーフェスが矛盾し、
どちらも理由を説明しない。100 Hz 変更はこれらの窓をすべて半分にした。

このうち S1-1 と併行して must-fix と扱う価値のあるのは 2 つだけ:
**S1-2**（エクスポートのメモリ / UI フリーズ、ローテート済みファイルへの直接 `readFileSync`）と
**S1-3**（webview で毎秒 21 800 回無駄な反復＋恒久的に誤ったフッター）。
S3-2 のトレース窓短縮は「壊れている」のではなく「正直だが伝わっていない」性质である。
