# 2026-11-21 — 修正・改善ラウンド（stm32-ext v2.0.7）

## 前提と方法

このリポジトリの `main`（`b02cb83`）を clone し、**テストが緑であることを確認してから**コードを読み直した。
前回の読み取り専用監査（[`docs/audit-2026-10-01.md`](audit-2026-10-01.md)）の指摘はすでに大半が
修正済みだったため、本ラウンドは (1) 監査の残件の再確認、(2) 監査後に追加された機能が
既存契約を壊していないかの確認、(3) 新規の不具合探索、の 3 つを行った。

**着手時の状態は緑ではなかった。** clone 直後の `npm run verify` は 10 件失敗した（後述 F-7）。
すべての修正は `npm run verify` と、破壊した契約を固定する回帰テストで裏づけている。

## 不具合（正しさ・安全）

### F-1 · 壊れたロックファイルが VSCode 本体を殺せた · **証明済み（修正）**

`/tmp/stm32ext-live.lock` の `pid` は検証されずに `process.kill(pid, 0)` と
`process.kill(pid, "SIGTERM")` に渡っていた（`src/extension.ts` の `claimProbe` /
`killForeignSession`）。`kill(0, SIGTERM)` は**自分自身のプロセスグループ**へのシグナル、
`kill(-7, …)` は別のプロセスグループへのシグナルなので、壊れた・古い形式のロック 1 個で
拡張ホスト（VSCode）を落とせた。

**修正**: `src/live/manager.ts:35` の `isUsablePid`（正の安全な整数のみ）を
`readSessionLock` のパース地点（`:43`）に置き、非正・非整数・NaN・巨大値は
「ロック無し」として扱う。`isPidAlive`（`:65`）も同じ関門を通す。

**回帰テスト**: `tests/live-manager.test.ts` の
「a lock pid may never reach kill() as a process group」（0 / -7 / -1 / 1.5 / NaN / Infinity / 2^60）。

### F-2 · 変数を書き込むたびに「別セッションがプローブ使用中」と出て、自分の監視を SIGTERM していた · **証明済み（修正）**

ロックが記録するのは**サイドカーの pid** なのに、書き込み前の強制奪取
（`src/extension.ts:1678` の旧 `killForeignSession`）は `lock.pid === process.pid`
（拡張ホストの pid）しか自分のものと見なしていなかった。両者は決して一致しないため、
**自分の監視セッションが常に「別セッション」と判定され**、モーダルで「強制終了する」を
選ぶと自分のサイドカーを SIGTERM していた。`b02cb83`/ `59183a6` はこの症状に触れているが、
比較対象が違うため直っていなかった。

**修正**: `isForeignSessionLock(lock, { childPid, hostPid }, alive)`（`src/live/manager.ts:86`）を
単一の判定とし、`killForeignSession`（`src/extension.ts:834`）と
`liveForeignHolderPid`（`:2013`）の両方がこれを使う。自分のロックは所有権も
stale 掃除も触らない。

### F-3 · 奪取をキャンセルしても書き込みが実行されていた · **証明済み（修正）**

`writeFlow` は `await this.killForeignSession()` の**戻り値を捨てていた**。
ユーザーがモーダルで「やめる」を選んでも、そのままバスへ書き込んでいた
（別セッションのプローブ越しに値を押し込む経路）。

**修正**: `foreignSessionStillHeld()`（`src/extension.ts:892`）が奪取を試み、
**その後もロックが生きていれば書き込みを拒否**する（`[live-write] … REFUSED(...)` の監査行つき、
`:1678`）。SIGTERM 後は pid の消滅を最大 2 秒待つ（`waitForPidExit`）ので、
プローブ解放前の書き込みで USB busy になる窓も縮む。

### F-4 · 書き込み・ビルド書込で、自分の監視セッションを「競合」と表示していた · **証明済み（修正）**

`checkProbeConflict` はロック保持者が誰でも競合としてモーダルを出していた。
フラッシュは直後に自分のセッションを止めるので、これは偽の競合であり、
「このまま続行」を押す習慣を作る。

**修正**: `opts.ownPid` を追加し（`src/extension.ts:181`）、フラッシュ 2 経路が
`live?.pollPid` を渡す（`:2088`, `:2185`）。

### F-5 · autoSetup が入れた pyocd を、書き込みだけが見つけられなかった · **証明済み（修正）**

初回セットアップは pyocd を**拡張専用 venv** に入れる。Live 監視は venv の python で
サイドカーを起動するので動くが、書き込みは `src/flash/pyocd.ts` の私有 PATH 探索
（`resolvePyocdPath`）だけを見ていた。結果、「拡張が入れた pyocd」しか無いマシンでは
監視はできるのに書き込みだけ `pyocd was not found on PATH` で失敗していた。
エラーメッセージも、PEP 668 で必ず失敗する `pip install --user pyocd` を案内していた
（README 自身がそれを否定している）。

**修正**: 探索を `resolveTool`（`src/build/backend.ts`）へ委譲（`src/flash/pyocd.ts:67`）。
PATH → `~/.local/bin` → セットアップ venv の順で探す。メッセージも自動導入と pipx/venv を案内する形に変更。

**回帰テスト**: `tests/pyocd-flash.test.ts` の「searches the setup venv, where autoSetup
actually installs pyocd」。

### F-6 · 監視リストを空にしても、次のビルドで全葉が埋め戻されていた · **証明済み（修正）**

`setResolution` は「監視リストが空」を「まだ決めていない」と同一視して、解決した葉を
すべて自動監視していた。ユーザーが最後の 1 個を「×」で外しても、再ビルドで全葉が戻る。
「意図して空」と「未設定」を区別できていなかった。

**修正**: `stm32ext.liveWatchInit`（`src/live/manager.ts:17`）を追加し、
自動シードは**一度だけ**。追加・削除もこのフラグを立てるので、空にした状態が保存される。

**回帰テスト**: `tests/no-session-log.test.ts` の
「auto-monitor seeds the watchlist once, then respects the user」。

### F-7 · clone 直後の `npm run verify` が赤だった（README の主張と矛盾） · **証明済み（修正）**

`verify` の順序が `typecheck → typecheck:tests → test → test:py → compile` で、
`tests/cli-entry.test.ts` の E2E 3 件は `out/cli/stm32.js` が無いと失敗する。
`out/` は `.gitignore` 済みなので、**clone 直後は必ず 3 件落ちる**。
README は「clone 直後で green」と書いていた。

**修正**: `package.json` の `verify` を `… → compile → test → test:py` に並べ替え。
fresh clone を別ディレクトリに作って実測した（下の検証ログ）。

### F-8 · 回帰テスト自体が不安定だった（2 件） · **証明済み（修正）**

- `tests/csv-export.test.ts`「leaves the event loop running」は `setTimeout(0)` の回数で
  yield を測っていた。Node は `setTimeout(0)` を 1ms にクランプするため、高速なマシンでは
  30 チャンクのコピーが 24ms で終わり **5 tick しか回らず必ず落ちる**。コピーと同じ
  `setImmediate` で数えるよう変更。
- 同ファイル「never holds more than one chunk in memory」は `heapUsed` の差で測っていた。
  正しい実装でもチャンクごとの Buffer ゴミで数 MB 増えるため、**正しい実装を落とす**
  テストだった。読み取り 1 回の最大バイト数（`onProgress` の差分）で測る形に変更。

### F-9 · 解像度ファイルが無いとトレースバックで exit 1 · **証明済み（修正）**

`scripts/live_poll.py` は `--resolution` の読み込みを無防備に行っていた。ホストは
3/4/5/6 しか説明できないので、traceback + exit 1 は「不明な失敗」になる。

**修正**: `live_poll.py:771` で読み込みを包み、ファイル名を名指しして exit 6
（文書化済みの「監視対象なし」）。**回帰テスト**: `tests/test_live_poll.py`
`test_missing_resolution_file_names_the_file_and_exits_6`。

## 改善（性能・UX・保守性）

### I-1 · グラフパネルが監視変数**全部**を毎バッチ受け取っていた

`GraphPanelProvider.pushSamples` は、Live の全量バッチ（監視 400 個なら 1 tick あたり 400 件）を
そのまま webview へ `postMessage` していた。グラフは系列しか描かないので、残りは
`Map.get` の空振り＋ブリッジのシリアライズだけ。さらにフッターは
`未登録 403` を恒久的に表示し、「403 個の変数が失敗した」と読めていた。

- ホスト側で**描画している系列だけ**に絞る（`src/extension.ts:1906`）。
- webview 側の `G.unknown` カウンタを削除（`src/live/graphPanel.ts`）。
  フッターは `系列 / 表示 / 保持上限` のみ。
- テストを新しい契約に更新（`tests/graph-panel.test.ts`, `tests/graph-forward.test.ts`）。

### I-2 · README と実装の食い違いを掃討

| 場所 | 旧記述 | 実際 |
|---|---|---|
| `stm32-ext/README.md` グラフ | 構造体追加は最大 32 葉、「未追加 N」表示 | 上限は撤去済み。全葉を追加する |
| 同・フッター | 「フレーム時間 p50/p95/max を表示」 | 計測行は削除済み（テストが不在を固定） |
| 同・書き込み結果 | 「下部の結果行に出ます」 | 変数タブの表の**上**（`var-note`）と行内 ✓/✗ |
| 同・系列履歴 | 「最大 20000 行」 | **全系列合計** 20000 行（系列数で時間幅が割られる） |
| 同・監視対象 | 記載なし | 初回ビルド時に自動シード（I-2 で 1 回だけに修正） |

### I-3 · 追跡されていた空の `stm32-ext/build.ninja`

0 バイトの生成物がコミットされ、VSIX にも同梱されていた。削除し、`.gitignore` に
`build.ninja` を追加（生成先は `build-ext/`）。

### I-4 · バージョン

`2.0.6` → `2.0.7`（`package.json` と `src/version.ts` はテストで同期を強制）。

## 確認したが修正不要だったもの

- 前回監査の S1-1（書き込みモーダル）、S1-2（CSV エクスポートのチャンク化）、
  S2-1（サイドバーの死んだ tree 機構）、S2-2（CLI venv の XDG 不一致）、
  S2-3〜S2-6、S3-1、S3-2、S3-3 は `main` で修正済み。今回のコードで再確認した。
- `live_poll.py` のブロック読み・tear guard・予算判定・CSV ローテーションは、
  ホスト側の tail（サイズ減少 + inode 変化でリセット）と整合していた。
- `allowlist.decideWrite` のコメント（モーダル必須・`confirmed=false` 拒否）は
  ホスト経路の実装と一致した。
- CLI `stm32` の stdout 単一 JSON 契約は、ユニット + 実プロセスの `--mock` E2E で確認。
